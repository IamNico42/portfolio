# Page Load Times und TCP Congestion Control

## Was ist die Page Load Time?

  

Die **Page Load Time** ist die Zeit, die ein Browser benötigt, um eine Webseite und ihre benötigten Objekte vollständig zu laden.

  

Eine Webseite besteht normalerweise nicht aus einer einzigen Datei. Der Browser lädt zuerst das HTML-Dokument. Darin befinden sich Verweise auf weitere Objekte, beispielsweise:

  

- Bilder

- Stylesheets

- JavaScript-Dateien

- Schriftarten

- Videos

  

Der Browser kann die zusätzlichen Objekte grundsätzlich erst anfordern, nachdem er ihre Adressen aus dem HTML-Dokument erfahren hat.

  

Die Page Load Time hängt deshalb sowohl vom HTTP-Verhalten als auch von TCP ab.

  

| Ebene | Entscheidet über |

|---|---|

| HTTP | wann und in welcher Reihenfolge Requests gestellt werden |

| TCP | wie viele Segmente gleichzeitig ohne Bestätigung gesendet werden dürfen |

| Netzwerk | RTT, Übertragungsrate, Paketverlust und Warteschlangen |

  

> HTTP-Pipelining und TCP Congestion Control sind zwei unterschiedliche Mechanismen. Pipelining macht mehr Requests verfügbar, hebt aber die Begrenzung durch das TCP Congestion Window nicht auf.

  

Eine DNS-Auflösung kann die reale Ladezeit zusätzlich verlängern. In den folgenden vereinfachten Berechnungen wird sie nur berücksichtigt, wenn sie in der Aufgabe ausdrücklich angegeben ist.

  

---

  

## Grundbegriffe

  

### RTT

  

Die **Round Trip Time (RTT)** ist die Zeit für eine Übertragung vom Sender zum Empfänger und die anschließende Rückmeldung zum Sender.

  

Bei einer vereinfachten HTTP-Betrachtung entspricht eine RTT beispielsweise der Zeit zwischen dem Absenden eines Requests und dem Eintreffen des ersten Teils der Antwort.

  

### MSS

  

Die **Maximum Segment Size (MSS)** gibt an, wie viele TCP-Nutzdaten ein einzelnes Segment maximal enthalten kann.

  

Beispiel:

  

```text

MTU: 1500 Byte

IPv4-Header: 20 Byte

TCP-Header: 20 Byte

MSS: 1460 Byte

```

  

In der früheren Übungsaufgabe gilt:

  

```text

MSS = 800 Byte

```

  

### IW

  

Das **Initial Window (IW)** ist der Startwert des Congestion Windows einer neuen TCP-Verbindung.

  

Bei:

  

```text

IW = 2 MSS

MSS = 800 Byte

```

  

darf der Sender anfangs höchstens zwei Segmente beziehungsweise 1600 Byte unbestätigte TCP-Nutzdaten senden.

  

### ACK

  

Ein ACK bestätigt bereits empfangene TCP-Daten.

  

TCP verwendet kumulative Bestätigungen. Ein ACK bestätigt damit nicht nur ein einzelnes Segment, sondern alle zusammenhängenden Daten bis zur angegebenen Position.

  

Im vereinfachten Segmentmodell gilt:

  

```text

ACK n bestätigt die Segmente S1 bis S(n-1).

```

  

Beispiel:

  

```text

ACK 4 bestätigt S1, S2 und S3.

```

  

Im echten TCP enthält die ACK-Nummer die Nummer des nächsten erwarteten Bytes.

  

---

  

## Von Bytes zu TCP-Segmenten

  

Für Page-Load-Aufgaben muss zunächst berechnet werden, aus wie vielen TCP-Segmenten ein Request oder eine Antwort besteht.

  

$$

\text{Segmente}

=

\left\lceil

\frac{\text{Datenmenge}}{\text{MSS}}

\right\rceil

$$

  

### Beispiel

  

Bei einer MSS von 800 Byte:

  

| Objekt | Größe | Benötigte Segmente |

|---|---:|---:|

| HTML-Dokument | 2000 Byte | 3 |

| Bild 1 | 3200 Byte | 4 |

| Bild 2 | 800 Byte | 1 |

| Bild 3 | 8000 Byte | 10 |

  

Für das HTML-Dokument gilt:

  

$$

\left\lceil\frac{2000}{800}\right\rceil

=

\left\lceil2{,}5\right\rceil

=3

$$

  

Das letzte Segment ist nur teilweise gefüllt.

  

---

  

## Persistent HTTP

  

Bei **Persistent HTTP** wird dieselbe TCP-Verbindung für mehrere HTTP-Requests und Responses wiederverwendet.

  

Dadurch muss nicht für jedes Bild und jede weitere Datei eine neue TCP-Verbindung aufgebaut werden.

  

Vorteile:

  

- weniger TCP-Handshakes

- weniger zusätzliche RTTs

- das bereits gewachsene `cwnd` kann für spätere Objekte weiterverwendet werden

  

Ob Requests trotzdem nacheinander oder gemeinsam gestellt werden dürfen, hängt vom Pipelining ab.

  

---

  

## Persistent HTTP ohne Pipelining

  

### Was bedeutet das?

  

Ohne Pipelining darf der Client auf einer persistenten Verbindung nur einen noch nicht beantworteten HTTP-Request besitzen.

  

Der Browser fordert ein Objekt an und wartet auf dessen vollständige Antwort. Erst danach stellt er den Request für das nächste Objekt.

  

### Kontext

  

Angenommen, eine Seite besteht aus:

  

- einem HTML-Dokument

- Bild 1

- Bild 2

- Bild 3

  

Der Ablauf besteht aus getrennten Request-Response-Runden:

  

1. Das HTML-Dokument wird angefordert und vollständig übertragen.

2. Bild 1 wird angefordert und vollständig übertragen.

3. Bild 2 wird angefordert und vollständig übertragen.

4. Bild 3 wird angefordert und vollständig übertragen.

  

Auch wenn TCP bereits viele Segmente gleichzeitig senden könnte, kennt der Server ohne den nächsten HTTP-Request noch nicht das nächste gewünschte Objekt.

  

### Vereinfachte Page Load Time für kleine Objekte

  

Werden Übertragungsdauer, Slow Start und Verbindungsaufbau zunächst ignoriert, benötigt jedes nacheinander angeforderte Objekt ungefähr eine eigene RTT.

  

Für ein HTML-Dokument und $N$ eingebettete Objekte gilt bei bereits bestehender TCP-Verbindung:

  

$$

t_{\text{ohne Pipelining}}

\approx

(N+1)\cdot RTT

$$

  

Bei drei Bildern:

  

$$

t_{\text{ohne Pipelining}}

\approx

4\cdot RTT

$$

  

Ist die TCP-Verbindung noch nicht aufgebaut, kommt für den TCP-Handshake normalerweise eine weitere RTT hinzu.

  

---

  

## Persistent HTTP mit Pipelining

  

### Was bedeutet das?

  

Mit Pipelining kann der Client mehrere HTTP-Requests hintereinander senden, ohne jeweils die vorherige Antwort abzuwarten.

  

Das HTML-Dokument muss weiterhin zuerst geladen beziehungsweise weit genug ausgewertet werden, damit der Browser die eingebetteten Objekte kennt.

  

Anschließend können die Requests für Bild 1, Bild 2 und Bild 3 gemeinsam gesendet werden.

  

### Antwortreihenfolge

  

Bei HTTP/1.1-Pipelining müssen die Antworten in der Reihenfolge der Requests übertragen werden.

  

Benötigt die erste Antwort sehr lange, können spätere Antworten nicht einfach an ihr vorbeiziehen. Dieses Problem heißt **Head-of-Line Blocking**.

  

### Vereinfachte Page Load Time für kleine Objekte

  

Unter der vereinfachten Annahme kleiner Objekte und einer bereits aufgebauten TCP-Verbindung werden ungefähr zwei HTTP-Runden benötigt:

  

1. Eine Runde für das HTML-Dokument.

2. Eine gemeinsame Runde für die eingebetteten Objekte.

  

Damit gilt näherungsweise:

  

$$

t_{\text{mit Pipelining}}

\approx

2\cdot RTT

$$

  

Bei einer neuen TCP-Verbindung kommt normalerweise eine RTT für den Verbindungsaufbau hinzu.

  

---

  

## Vergleich mit und ohne Pipelining

  

| Eigenschaft | Ohne Pipelining | Mit Pipelining |

|---|---|---|

| Anzahl gleichzeitig offener Requests | einer | mehrere |

| Request für nächstes Objekt | erst nach vollständiger vorheriger Antwort | direkt nach den anderen Requests |

| Benötigte HTTP-Warterunden | viele | weniger |

| Reihenfolge der Responses | Reihenfolge ergibt sich automatisch | muss der Request-Reihenfolge entsprechen |

| Zentrales Problem | viele RTTs | Head-of-Line Blocking |

  

### Wichtig für Aufgaben

  

Pipelining bestimmt, welche Responses der Server bereits senden könnte.

  

Das tatsächliche Senden wird weiterhin durch TCP begrenzt. Besitzt der Server ein `cwnd` von 4 MSS, darf er auch bei zehn bereits vorhandenen HTTP-Requests nur die durch das Fenster erlaubte Datenmenge unbestätigt senden.

## Was ist TCP Congestion Control?

  

TCP Congestion Control verhindert, dass ein Sender zu viele Daten gleichzeitig in das Netzwerk gibt.

  

TCP kennt die Auslastung der einzelnen Router und Leitungen nicht direkt. Es beobachtet stattdessen:

  

- welche Daten bestätigt werden

- wie schnell ACKs zurückkommen

- ob Duplicate ACKs auftreten

- ob ein Retransmission Timeout abläuft

  

Aus diesen Rückmeldungen passt TCP sein Congestion Window an.

  

---

  

## Congestion Window

  

Das **Congestion Window (`cwnd`)** ist ein senderseitiger Wert.

  

Es begrenzt die Menge der noch nicht bestätigten Daten, die gleichzeitig im Netz sein darf.

  

Vereinfacht gilt:

  

$$

\text{FlightSize}\leq cwnd

$$

  

### FlightSize

  

Die FlightSize ist die Menge der bereits gesendeten, aber noch nicht bestätigten Daten.

  

In einer tabellarischen Aufgabe können zwei Zustände betrachtet werden:

  

| Zustand | Bedeutung |

|---|---|

| FlightSize nach ACK-Empfang | noch unbestätigte Daten, nachdem neue Bestätigungen berücksichtigt wurden |

| FlightSize nach dem Senden | unbestätigte Daten, nachdem der Sender sein Fenster erneut gefüllt hat |

  

### Freier Platz im Fenster

  

Vereinfacht kann der Sender neu senden:

  

$$

\text{freie Segmente}

=

cwnd-\text{FlightSize}

$$

  

Beispiel:

  

```text

cwnd = 6 MSS

FlightSize = 4 MSS

```

  

Der Sender darf zwei weitere Segmente senden.

  

In echtem TCP begrenzt zusätzlich das vom Empfänger gemeldete Receive Window die sendbare Datenmenge. In einer reinen Congestion-Control-Aufgabe wird diese zusätzliche Begrenzung häufig ignoriert.

  

---

  

## Slow Start

  

### Was ist das?

  

Slow Start ist die erste Wachstumsphase des Congestion Windows.

  

Der Name bedeutet nicht, dass `cwnd` besonders langsam wächst. Das Fenster beginnt klein, wächst aber ungefähr exponentiell.

  

### Wachstum

  

Für jedes neu bestätigte MSS erhöht sich `cwnd` während Slow Start näherungsweise um ein MSS.

  

$$

cwnd_{\text{neu}}

=

cwnd_{\text{alt}}+1\,MSS

\quad\text{pro neu bestätigtem MSS}

$$

  

Da innerhalb einer RTT mehrere Segmente bestätigt werden können, verdoppelt sich das Fenster ungefähr pro RTT.

  

### Beispiel mit `IW = 2 MSS`

  

| Senderunde | `cwnd` vor dem Senden | maximal sendbare Segmente | `cwnd` nach vollständiger Bestätigung |

|---:|---:|---:|---:|

| 1 | 2 MSS | 2 | ungefähr 4 MSS |

| 2 | 4 MSS | 4 | ungefähr 8 MSS |

| 3 | 8 MSS | 8 | ungefähr 16 MSS |

  

Die Tabelle gilt nur, wenn:

  

- genügend Daten vorhanden sind

- jedes Segment bestätigt wird

- keine Delayed ACKs berücksichtigt werden

- kein Paketverlust auftritt

- `ssthresh` noch nicht erreicht ist

  

---

  

## Wie viele Senderunden benötigt Slow Start?

  

Bei idealisiertem Slow Start mit vollständiger Verdopplung werden in den einzelnen Runden folgende Segmentmengen gesendet:

  

```text

IW, 2 · IW, 4 · IW, 8 · IW

```

  

Nach $k$ Runden wurden insgesamt übertragen:

  

$$

IW\cdot(2^k-1)

$$

  

Für ein Objekt mit $S$ Segmenten wird die kleinste Rundenzahl gesucht, für die gilt:

  

$$

IW\cdot(2^k-1)\geq S

$$

  

### Beispiel

  

Ein Bild besteht aus 10 Segmenten und `IW = 2 MSS`.

  

| Senderunde | Segmente dieser Runde | Insgesamt |

|---:|---:|---:|

| 1 | 2 | 2 |

| 2 | 4 | 6 |

| 3 | höchstens 8, benötigt werden noch 4 | 10 |

  

Das Bild benötigt unter diesen vereinfachten Bedingungen drei TCP-Senderunden.

  

---

  

## `ssthresh` und Congestion Avoidance

  

### Was ist `ssthresh`?

  

`ssthresh` ist der **Slow Start Threshold**.

  

Er bestimmt, wann TCP vom schnellen Wachstum des Slow Starts zum vorsichtigeren Wachstum der Congestion Avoidance wechselt.

  

| Bedingung | Phase |

|---|---|

| `cwnd < ssthresh` | Slow Start |

| `cwnd >= ssthresh` | Congestion Avoidance |

  

`ssthresh` ist damit keine eigene Phase. Es ist die Grenze zwischen zwei Wachstumsphasen.

  

---

  

## Congestion Avoidance

  

### Was ist das?

  

In der Congestion Avoidance wächst `cwnd` nicht mehr ungefähr exponentiell, sondern nur noch ungefähr linear.

  

Über eine vollständige RTT steigt das Fenster insgesamt um ungefähr ein MSS.

  

$$

cwnd_{\text{neu}}

\approx

cwnd_{\text{alt}}+1\,MSS

\quad\text{pro RTT}

$$

  

Das Wachstum wird in der Praxis auf die einzelnen ACKs verteilt.

  

Eine typische vereinfachte Berechnung pro ACK lautet:

  

$$

cwnd_{\text{neu}}

=

cwnd_{\text{alt}}+\frac{MSS^2}{cwnd_{\text{alt}}}

$$

  

### Beispiel

  

| RTT | `cwnd` vorher | `cwnd` danach |

|---:|---:|---:|

| 1 | 8 MSS | ungefähr 9 MSS |

| 2 | 9 MSS | ungefähr 10 MSS |

| 3 | 10 MSS | ungefähr 11 MSS |

  

Dieses Verhalten heißt **Additive Increase**.

  

---

  

## Warum existieren zwei Wachstumsphasen?

  

Zu Beginn kennt TCP die verfügbare Kapazität des Pfads nicht.

  

Slow Start erhöht die Senderate schnell, damit die Verbindung nicht lange ungenutzt bleibt.

  

Ab `ssthresh` geht TCP vorsichtiger vor. Congestion Avoidance tastet sich schrittweise an zusätzliche Kapazität heran, ohne das Netz sofort wieder stark zu belasten.

  

---

  

## Zusammenhang zwischen Page Load Time und `cwnd`

  

### Kleine Antwort

  

Passt die gesamte HTTP-Response in das aktuelle `cwnd`, kann der Server alle Segmente unmittelbar senden.

  

Die Ladezeit wird dann hauptsächlich durch die RTT und das HTTP-Verhalten bestimmt.

  

### Große Antwort

  

Ist die Response größer als `cwnd`, muss der Server zunächst auf ACKs warten.

  

Erst nach den Bestätigungen darf er weitere Segmente senden. Dadurch entstehen zusätzliche TCP-Senderunden.

  

### Ohne Pipelining

  

Nach der vollständigen Übertragung eines Objekts muss der Server zusätzlich auf den nächsten HTTP-Request warten.

  

Die Ladezeit enthält deshalb:

  

- TCP-Warterunden innerhalb einer großen Response

- zusätzliche HTTP-Warterunden zwischen den Objekten

  

### Mit Pipelining

  

Die Requests für mehrere Objekte liegen dem Server bereits vor.

  

Sobald durch neue ACKs Platz im Congestion Window entsteht, kann der Server Daten des nächsten Objekts senden. Die Responses müssen bei HTTP/1.1-Pipelining trotzdem in der vorgegebenen Reihenfolge bleiben.

  

---

  

## Beispiel mit `MSS = 800 Byte` und `IW = 2 MSS`

  

Gegeben sind:

  

| Objekt | Request | Request-Segmente | Response | Response-Segmente |

|---|---:|---:|---:|---:|

| HTML | 1200 Byte | 2 | 2000 Byte | 3 |

| Bild 1 | 1600 Byte | 2 | 3200 Byte | 4 |

| Bild 2 | 3200 Byte | 4 | 800 Byte | 1 |

| Bild 3 | 4800 Byte | 6 | 8000 Byte | 10 |

  

### HTML-Response

  

Die HTML-Response besteht aus drei Segmenten.

  

Der Server startet mit:

  

```text

cwnd = 2 MSS

```

  

In der ersten Senderunde kann er zwei Segmente übertragen. Nach deren Bestätigung ist das Fenster größer und das letzte Segment kann gesendet werden.

  

Die HTML-Response benötigt deshalb unter den vereinfachten Annahmen zwei TCP-Senderunden.

  

### Danach ohne Pipelining

  

Nach dem vollständigen HTML-Dokument stellt der Browser den Request für Bild 1.

  

Erst wenn Bild 1 vollständig angekommen ist, folgt der Request für Bild 2. Danach folgt Bild 3.

  

Das bereits durch die HTML-Übertragung gewachsene `cwnd` bleibt auf der persistenten TCP-Verbindung erhalten.

  

### Danach mit Pipelining

  

Nach dem vollständigen HTML-Dokument kann der Browser die Requests für Bild 1, Bild 2 und Bild 3 hintereinander senden.

  

Der Server kennt dadurch bereits alle angeforderten Objekte. Er überträgt die Responses in Request-Reihenfolge und füllt dabei sein jeweils verfügbares Congestion Window.

  

---

  

## Paketverlust und Duplicate ACKs

  

TCP erkennt Paketverlust nicht durch eine direkte Verlustmeldung.

  

Kommt ein späteres Segment an, obwohl ein vorheriges Segment fehlt, bestätigt der Empfänger weiterhin nur die letzte zusammenhängend empfangene Datenposition.

  

Dadurch entstehen mehrere ACKs mit demselben Wert. Diese werden **Duplicate ACKs** genannt.

  

### Beispiel

  

Der Sender überträgt:

  

| Segment | Bytebereich | Ergebnis |

|---|---|---|

| Segment 1 | 0 bis 799 | kommt an |

| Segment 2 | 800 bis 1599 | kommt an |

| Segment 3 | 1600 bis 2399 | geht verloren |

| Segment 4 | 2400 bis 3199 | kommt an |

| Segment 5 | 3200 bis 3999 | kommt an |

| Segment 6 | 4000 bis 4799 | kommt an |

  

Nach Segment 2 erwartet der Empfänger Byte 1600.

  

Da Segment 3 fehlt, erzeugen die später eintreffenden Segmente weiterhin Bestätigungen für Byte 1600.

  

Nach drei Duplicate ACKs erkennt der Sender den wahrscheinlichen Verlust.

  

---

  

## Fast Retransmit

  

Bei drei Duplicate ACKs sendet TCP das vermutlich verlorene Segment sofort erneut.

  

Es muss nicht auf den Retransmission Timeout warten.

  

Diese Aktion heißt **Fast Retransmit**.

  

Die drei Duplicate ACKs zeigen gleichzeitig, dass spätere Segmente noch durch das Netz gelangen. TCP nimmt deshalb normalerweise keine so starke Überlast an wie bei einem Timeout.

  

---

  

## Fast Recovery

  

Für die klassische TCP-Reno-Betrachtung gilt bei drei Duplicate ACKs:

  

$$

ssthresh

=

\max\left(\frac{FlightSize}{2},2\,MSS\right)

$$

  

In vereinfachten Aufgaben wird häufig verwendet:

  

$$

ssthresh=\frac{cwnd}{2}

$$

  

Beim Eintritt in Fast Recovery gilt:

  

$$

cwnd=ssthresh+3\,MSS

$$

  

Die zusätzlichen drei MSS berücksichtigen die drei Duplicate ACKs und damit drei Segmente, die das Netz bereits verlassen haben.

  

Für jeden weiteren Duplicate ACK kann `cwnd` vorübergehend um ein weiteres MSS erhöht werden.

  

Bestätigt ein neues ACK schließlich die geschlossene Lücke, gilt:

  

$$

cwnd=ssthresh

$$

  

Anschließend arbeitet TCP in Congestion Avoidance weiter.

  

---

  

## Retransmission Timeout

  

Ein Timeout tritt auf, wenn innerhalb der berechneten Wartezeit keine ausreichende Bestätigung eintrifft.

  

TCP wertet einen Timeout als stärkeres Überlastsignal als drei Duplicate ACKs.

  

Für eine vereinfachte Aufgabe gilt:

  

$$

ssthresh=\frac{cwnd}{2}

$$

  

Danach wird das Congestion Window stark reduziert:

  

$$

cwnd=1\,MSS

$$

  

TCP beginnt erneut mit Slow Start.

  

> Ein Timeout tritt nicht allgemein nach genau zehn RTTs auf. Diese Annahme gilt nur, wenn sie in der konkreten Aufgabe vorgegeben wird.

  

---

  

## Vergleich der Verlustreaktionen

  

| Ereignis | Interpretation | Reaktion |

|---|---|---|

| drei Duplicate ACKs | einzelne Lücke, aber weitere Daten kommen an | Fast Retransmit und Fast Recovery |

| Retransmission Timeout | keine ausreichende Rückmeldung | `cwnd` stark reduzieren und Slow Start neu beginnen |

  

### Nach drei Duplicate ACKs

  

- verlorenes Segment sofort erneut senden

- `ssthresh` ungefähr auf die Hälfte setzen

- Fast Recovery durchführen

- anschließend Congestion Avoidance

  

### Nach Timeout

  

- fehlende Daten erneut senden

- `ssthresh` ungefähr auf die Hälfte setzen

- `cwnd` auf ein MSS setzen

- Slow Start neu beginnen

  

---

  

## AIMD

  

Das grundlegende Verhalten von TCP wird häufig als **Additive Increase, Multiplicative Decrease** beschrieben.

  

### Additive Increase

  

Solange kein Verlust auftritt, wächst `cwnd` in Congestion Avoidance ungefähr um ein MSS pro RTT.

  

### Multiplicative Decrease

  

Bei erkannter Überlast wird das Fenster deutlich reduziert, häufig ungefähr halbiert.

  

Dadurch tastet sich TCP langsam an zusätzliche Kapazität heran und reagiert deutlich auf Überlast.

## Vorgehensweise bei einer Page-Load-Aufgabe

  

### Schritt 1: Aufgabenannahmen notieren

  

Prüfe:

  

- Ist die TCP-Verbindung bereits aufgebaut?

- Ist HTTP persistent?

- Ist Pipelining erlaubt?

- Welche MSS gilt?

- Welches IW gilt?

- Welcher Wert ist für `ssthresh` gegeben?

- Gibt es Paketverluste?

- Wie werden ACKs in der Aufgabe modelliert?

  

### Schritt 2: Requests und Responses segmentieren

  

Berechne für jedes Objekt:

  

$$

\text{Segmente}

=

\left\lceil

\frac{\text{Bytes}}{\text{MSS}}

\right\rceil

$$

  

### Schritt 3: HTTP-Abhängigkeiten bestimmen

  

Das HTML-Dokument muss zuerst verfügbar sein.

  

Ohne Pipelining darf der nächste Objekt-Request erst nach der vollständigen vorherigen Response gesendet werden.

  

Mit Pipelining können die bekannten Objekt-Requests gemeinsam gestellt werden.

  

### Schritt 4: TCP-Fenster anwenden

  

Für jeden Sender getrennt bestimmen:

  

- aktuelles `cwnd`

- aktuelle FlightSize

- durch neue ACKs bestätigte Segmente

- freien Platz im Fenster

- neu sendbare Segmente

  

### Schritt 5: Wachstumsphase bestimmen

  

| Bedingung | Verhalten |

|---|---|

| `cwnd < ssthresh` | Slow Start |

| `cwnd >= ssthresh` | Congestion Avoidance |

| drei Duplicate ACKs | Fast Retransmit und Fast Recovery |

| Timeout | `cwnd` stark reduzieren und Slow Start |

  

### Schritt 6: Vollständige Ladezeit bestimmen

  

Die Seite ist erst vollständig geladen, wenn:

  

- das HTML-Dokument vollständig angekommen ist

- alle benötigten Objekt-Requests gesendet wurden

- alle Responses vollständig angekommen sind

- erforderliche Retransmissions abgeschlossen sind

## Häufige Fehler

  

### Pipelining mit einem größeren `cwnd` verwechseln

  

Pipelining erlaubt mehrere HTTP-Requests. Es vergrößert nicht automatisch das TCP-Fenster.

  

### Bilder vor dem HTML-Dokument anfordern

  

Der Browser kennt die eingebetteten Objekte normalerweise erst aus dem HTML-Dokument.

  

### `cwnd` von Client und Server gleichsetzen

  

Jede Senderichtung besitzt ein eigenes Congestion Window.

  

Der Client verwendet sein Fenster für Requests. Der Server verwendet sein Fenster für Responses.

  

### Pro ACK immer nur ein Segment als bestätigt betrachten

  

TCP-ACKs sind kumulativ. Ein ACK kann mehrere seit dem vorherigen ACK neu bestätigte Segmente umfassen.

  

### Bei jedem Verlust sofort einen Timeout annehmen

  

Kommen nachfolgende Segmente an, kann der Verlust bereits durch drei Duplicate ACKs erkannt werden.

  

### `ssthresh` als eigene TCP-Phase behandeln

  

`ssthresh` ist eine Grenze. Die Phasen heißen Slow Start, Congestion Avoidance und je nach Verfahren Fast Recovery.

  

### Timeout nach einer festen Zahl von RTTs annehmen

  

Der Retransmission Timeout wird aus gemessenen Zeiten berechnet. Eine feste Zahl wie zehn RTTs gilt nur als konkrete Aufgabenannahme.

## Zusammenfassung der wichtigsten Begriffe

  

| Begriff | Bedeutung |

|---|---|

| Page Load Time | Zeit bis alle benötigten Seitenobjekte geladen sind |

| Persistent HTTP | mehrere HTTP-Übertragungen auf derselben TCP-Verbindung |

| Pipelining | mehrere Requests senden, ohne die einzelnen Responses abzuwarten |

| Head-of-Line Blocking | eine frühe Response blockiert spätere Responses |

| MSS | maximale TCP-Nutzdaten pro Segment |

| IW | Startwert des Congestion Windows |

| `cwnd` | senderseitige Begrenzung unbestätigter Daten |

| FlightSize | bereits gesendete, aber noch nicht bestätigte Daten |

| `ssthresh` | Grenze zwischen Slow Start und Congestion Avoidance |

| Slow Start | ungefähr exponentielles Wachstum |

| Congestion Avoidance | ungefähr lineares Wachstum |

| Duplicate ACK | wiederholte Bestätigung derselben nächsten Datenposition |

| Fast Retransmit | sofortige Neuübertragung nach drei Duplicate ACKs |

| Fast Recovery | moderate Fensteranpassung nach drei Duplicate ACKs |

| Timeout | fehlende Bestätigung innerhalb des RTO |

  

---

  

## Fazit

  

- Das HTML-Dokument muss grundsätzlich zuerst geladen werden, weil es die weiteren Objekte beschreibt.

- Ohne Pipelining entstehen zusätzliche HTTP-Warterunden zwischen den einzelnen Objekten.

- Mit Pipelining können mehrere Objekt-Requests gemeinsam gestellt werden.

- TCP begrenzt unabhängig davon die gleichzeitig unbestätigte Datenmenge durch `cwnd`.

- Slow Start erhöht das Fenster ungefähr exponentiell.

- Ab `ssthresh` wächst das Fenster in Congestion Avoidance ungefähr linear.

- Drei Duplicate ACKs führen bei TCP Reno zu Fast Retransmit und Fast Recovery.

- Ein Timeout reduziert `cwnd` stärker und startet Slow Start erneut.

- Für eine vollständige Page-Load-Berechnung müssen HTTP-Abhängigkeiten und TCP-Senderunden gemeinsam betrachtet werden.
